## Licensing and attribution

- Application code is MIT licensed.
- DSAT, SMG, MLM, FSM, and OpenStreetMap data remain subject to their publishers' terms.
- Parking coordinates use OpenStreetMap (ODbL) and, for 14 car parks, the Macau SAR Government WebMap Carpark POI layer (DSSCU); government GIS data remains subject to its publisher's terms.
- OpenStreetMap-derived LRT geometry requires ODbL attribution.
- Camera streams are played directly from the publisher and are never recorded or re-hosted.
- Assistant answers are generated text from the configured provider. The app attributes the model in the response meta and stores neither questions nor answers.
- The public API exposes normalized current views and explicitly dated topology snapshots, not bulk history or raw upstream datasets.

## Adapter notes

- Journey presentation uses the existing normalized ETA API for each selected leg (maximum two). Stop codes, direction, segment chain, count and endpoint geometry must match before a bus line is drawn. Repeated ambiguous paths, missing segments and conflicting transfer coordinates are not joined with invented lines. Official schedules/operating hours remain unverified for bus journeys. `docs/qa/resident-workspace/bus-journey-accuracy.json` records fresh reads of routes 3A, MT5 and 25 and the 30-stop versus 9-stop ranking regression.
- Walking navigation is an outbound user action, not a data adapter: a plain Google Maps URL uses `api=1`, latitude/longitude endpoints and `travelmode=walking`, following [Google's Maps URLs documentation](https://developers.google.com/maps/documentation/urls/get-started). No request, key or embedded walking response is used by this app. The visible link discloses endpoint sharing. Straight access connectors are labelled as unverified walking paths; link generation never turns them into routed walking geometry.

- `lrt-service`: `/api/v1/lrt/service` returns normalized line names, weekday/weekend service hours, published frequency and whole-line journey descriptions, station timetable links and the publisher's revision note. The 2026-11-10 live response has three lines and 17 station/line timetable entries, all marked September 2026 by the publisher. Parse only `#content1` and `#content2`; the same HTML contains obsolete 2020 service text outside those sections. Timetable URLs must be local `/images/stations/TimeTable/` JPG/PNG paths and are resolved to MLM HTTPS. The browser opens the original publisher image. Images are not re-hosted or OCR-transcribed into predicted arrivals. Missing current markup fails validation and uses the shared stale fallback. Retrieval time is separate from the timetable edition. No live train position or live arrival field is exposed. See `LRT_DATA_AUDIT_2026-11-10.md`.

- `official-news`: `/api/v1/traffic/news` returns normalized `{ items, feeds }`. The government RSS directory lists both endpoints. On 2026-11-10 direct reads returned valid XML: 33 GCS items and 20 DSAT items. GCS items use `title`, `description`, ISO `pubDate`, `link` and `dc:creator`; DSAT uses RFC-style `pubDate`. GCS titles are filtered for transport terms; DSAT news is retained. Links are restricted to HTTPS and each publisher's own hostname. Summaries are stripped of HTML and capped at 240 characters. Identical titles are deduplicated; publication times remain those of the publishers. These are limited recent-news feeds, not a complete incident feed or proof that an event is still active. Every feed exposes availability; all-feed failure uses the shared stale fallback instead of an invented empty collection. No history is retained.
- `notices`: roadwork dates embedded in a title describe an effective window, not a publication timestamp. Those entries now return `publishedAt: null`. The UI keeps the window in the title and labels the collection as published announcements. The `incident` category is a keyword classification only; it does not establish an ongoing event. Failure of every DSAT page throws so the cache can retain valid older data.

- 2026-11-10 accuracy correction: `borders.estimatedWaitMinutes` remains nullable for compatibility and is now always null. The adapter previously generated 10/30/45/60 minutes from status codes; those values were not read from an official waiting-time field. The UI uses the official qualitative status. A direct request on this date received an HTML challenge, while the adapter verification later returned eight entries. Availability is variable. See `SOURCE_AUDIT_2026-11-10.md`.
- `parking.updatedAt` is now nullable. An absent or invalid publisher timestamp stays null; it is never replaced by the current time. Response metadata still records the server retrieval time separately.
- Client freshness uses elapsed time as well as response timestamps, so a previously fresh response becomes delayed after contact is lost. A catalog's freshness is not used as proof that its vehicle-location slice is current.

- `cameras`: the official catalog repeats some border cameras once per zone under a shared numeric id. The adapter keeps every zoned entry, drops byte-identical repeats, and appends a short deterministic suffix to colliding ids so map features, list keys, and camera selection stay stable.
- `lrt-network`: the server rebuilds the network from OpenStreetMap route relations every 6 hours. Lines are grouped by `ref`; stations are merged by name and proximity under 400 m, so 協和醫院 and 蓮花 stay interchanges. Known stations keep the curated official names and ids from `data/lrt-network.json`; new stations use the OSM name tags. Overpass endpoints are tried in order (`LRT_OVERPASS_URL` overrides them), and failures or a result with fewer than 3 lines or 15 stations fall back to the checked-in file. `npm run build:lrt` refreshes that file with the same builder. The map may show one train per selected line that moves along the OSM-derived alignment as an explicitly labelled schematic animation at a fixed display speed; it is not live data (ADR 0008).
- `roads`: DSAT publishes live levels for 1,268 monitored segments only. The map draws the full OpenStreetMap street network in grey underneath, and no status is claimed for roads outside the official set.
- `bus-routes`: route coverage changes with the publisher's catalog. The 2026-11-10 build obtained 90 live routes. The official route page can add seasonal services omitted by the arrival catalog; those supplemental routes are returned with `live: false`.
- `bus-routes`: the catalog is fetched from DSAT at runtime every 6 hours. A new route appears without a redeploy; the cache keeps the previous list while the refresh runs.
- `bus-routes`: the official `routeChange` flag is set for 50 of 97 routes and the message endpoint answers `routeChange: true` for routes without suspended stops, so the UI no longer badges that flag. Diversions are shown only when `bus-diversion-{routeName}` reports suspended stops.
- `parking`: `data/parking-locations.json` maps the DSAT car park ids to OpenStreetMap `amenity=parking` coordinates (ODbL) by name. `npm run build:parking` regenerates the file from the DSAT list and an Overpass mirror, then falls back to the DSSCU WebMap Carpark POI layer (`https://webmap.gis.gov.mo/arcgis/rest/services/WebMap/MacauMap_P_POI/MapServer/8`, queried with `outSR=4326`) for names OSM does not match. All 92 current car parks have coordinates: 78 from OpenStreetMap and 14 from the Macau GIS layer. The GIS query is build-time only; the runtime reads the checked-in file and makes no GIS request. Occupancy still comes only from DSAT.
- `notices`: the adapter reads the three DSAT lists (特別消息 `emergency.aspx`, 交通改道 `croad.aspx`, 巴士改道 `bus_croad.aspx`) and recovers the location summary that the 特別消息 list hides inside an HTML comment. Incident keywords remain parser categories only. The UI shows these as published arrangements, separate from government RSS news. A selected announcement can match named monitored roads on the map; this does not verify an accident location or whether an event is ongoing. The sources checked in this revision did not establish a complete, reusable live incident feed. See `SOURCE_AUDIT_2026-11-10.md` for the bounded investigation and connection failures.
- `bus-eta-{code}-{direction}`: DSAT publishes no per-stop arrival minutes. The adapter reads the stop each live bus is approaching from `routestation/bus` and the position estimate the same publisher maintains per plate from `busInfoList` in `routestation/location`. The response marks these estimates with `positionSource: "feed"`. A vehicle without a published estimate falls back to its approached stop with `positionSource: "stop"`. The journey map and vehicle details use the shared freshness rule: a feed estimate remains visible during normal cache revalidation (TTL plus the existing eight-second grace window, ten seconds for bus data). Missing metadata, read errors or older data hide current vehicle positions. The source note keeps showing the actual retrieval time. Positions carry `estimated: true`.
- `bus-eta-{code}-{direction}`: the endpoint `/ddbus/app/passenger/route` is the passenger waiting-time/flow statistics feed behind the official 乘客候車時間 page (half-hour `seg` values, `currentSeg`, `historyRange`, and per-stop `average`/`current` counts). The adapter no longer reads it, and the panel never presents its counts as arrival minutes.
- `bus-eta-{code}-{direction}`: each stop carries `stopsAway`, the number of stops remaining before the next bus reaches it, computed from the approached stop sequences (`routeType: 2` circular routes wrap around the loop). 0 means a bus is heading to that stop. The panel labels 0 as 即將進站 with the plate and shows the remaining count on later stops, matching the official widget's 還有 N 站 count. No minute conversion is made, and stops behind every live bus show a dash on line routes.
- `bus-eta-{code}-{direction}`: the client concatenates the official stop-to-stop segments into one path and glides each marker from its drawn position toward the publisher's newest position estimate at a bounded bus speed, so a coarse step changes distance and direction smoothly and the marker holds when the estimate does not change. Loop routes continue into the next lap. The marker no longer rewinds to the stop just reached when the feed advances.
- `bus-eta-{code}-{direction}`: The official map page draws `route/traffic` as one polyline per stop-to-stop segment. Each returned segment carries `fromStationCode` and `toStationCode`, and its traffic level (1 normal, 2 slow, 3 congested, 4 very congested, -1 unknown) feeds the route line and stop badges. Invalid segments are omitted without shifting later pairings.
- `bus-eta-{code}-{direction}`: The upstream `busType` value is exposed on each vehicle. It is descriptive only; the model does not claim a brand or vehicle type.
- The map ground is flat. The optional 3D view tilts the camera and shows extruded buildings from the OpenFreeMap vector tiles; no terrain elevation source is loaded, so roads stay level.
- Transit models are schematic Blender 5.2 assets, rebuilt from operator photographs and the user's bus-stop reference. `scripts/build-transit-models.py` generates five self-contained GLBs and transparent home-screen button artwork. Buses use operator liveries without a verified plate-to-model mapping. The sign uses stacked cylindrical cabinets; LRT has a platform with a central guideway and a rounded single-carriage mesh instantiated twice. Each carriage follows its own track pose. See `models/REFERENCES.md`. Three.js loads only in 3D; required GLBs load from z14, with LRT carriages available from z12. All kinds use the same fixed 4x world-space schematic display scale. Zoom affects camera projection only; there is no screen-size compensation or high-zoom size cap. Two-car spacing uses the same constant. Landmark overlap is culled with the selected station first. Flat markers remain after model failure. Hidden mobile maps and reduced-motion preferences stop continuous animation.
- Day/night mode recolours the existing OpenFreeMap base layers in the browser. It uses the same style/tile endpoints and leaves application traffic colours unchanged. Parking distances use location only in the browser. AI journey requests separately obtain location and send it to the app server and configured provider, as disclosed beside the input. These inputs are not cached, persisted or explicitly logged by the app.
- `assistant`: the server assembles a compact JSON snapshot from the cached normalized contracts (roads with congested, slow, and question-matched segments; bridges; weather; parking; borders; notices; government transport RSS news and source timestamps/stale state; LRT notices; the LRT network with lines, stations, and interchanges) and adds live bus detail when the question names a route or a route is focused in the app: both directions for a single named route, capped at three route-direction slices, each with the full stop list, vehicles, approaching stops, stops-away counts, suspended stops, and per-segment traffic. Snapshot source status includes normalized source ids, retrieval times and stale flags for the bus catalogue and each requested route/direction as well as the general sources. The assistant must identify delayed bus data as the last retrieved estimate. Raw upstream payloads are never forwarded; vehicle positions are the publisher's own estimated coordinates, never presented as GPS, and the prompt forbids converting stops-away counts into minutes. When the question asks whether a route serves a place, the server checks the official stop list and the verified yes or no leads the answer, so the model cannot flip it. Answers can carry a UI action (focus a bus route or an LRT line) that the client applies to the map. The prompt fixes the explanation format, the locale, the snapshot citation, and the no-personal-data rule; `assistantConfigured()` disables the route when `SOURCE_ASSISTANT_ENABLED=false` or `ASSISTANT_API_KEY` is missing. Provider configuration is `ASSISTANT_API_KEY`, `ASSISTANT_BASE_URL`, `ASSISTANT_MODEL`, `ASSISTANT_TIMEOUT_MS`, and `ASSISTANT_RATE_LIMIT_PER_MINUTE`; the key stays server-side. The default provider is DeepSeek; a local OpenAI-compatible server such as Ollama can be used for offline demonstrations.

## Reference material not used

`bus_route/` is local reference material and is not committed (see `.gitignore`).

- `route_list.json` duplicates the live `getRouteAndCompanyList.html` response.
- `routes.json` is text extracted from the official route PDFs. Stop names are garbled by the PDF layout, there is no geometry, and 1 of 91 routes failed to parse, so it is not a reliable source.
- `stops.json` holds official Macau GIS bus-stop coordinates, but the live `routestation/location` endpoint already returns per-route stop coordinates in route order.
- The PDFs are raster route maps, so they cannot provide the official route alignment as coordinates.

## LRT corrections on 2026-11-10

- Track-way assembly now joins shared endpoints at both ends. The previous tail-only greedy algorithm inserted an artificial 1.53 km jump in the checked-in Taipa geometry. Disconnected ways are rejected, not bridged. Terminal overrun beyond the first/last stop is trimmed when the source contains those stop coordinates.
- The fallback was rebuilt from bounded OSM API reads of relations `10402162`, `18238277` and `18361945`. Runtime discovery still uses the existing Overpass endpoints and six-hour shared cache. No new OSM editing-API polling was added. `docs/qa/resident-workspace/lrt-geometry.json` records provenance, counts and the normalized-data hash.
- `stations[].lineCoordinates` is an optional normalized per-line coordinate map. Interchanges retain stable ids and a canonical coordinate while preserving the separate physical stop positions for each line. Selected-line markers, platform models and camera focus use that line's coordinate. Geometry is community-mapped track alignment, not official survey or live vehicle location.
- MLM RSS currently returns two September 2024 notices with `show=false`. The parser now retains both items, honours explicit display flags and interprets publisher CST as UTC+08:00. The legacy `active` field means publisher display status, not verified ongoing disruption. Hidden items are collapsed as history; missing flags do not become active. The assistant receives only displayed notices with publication dates and must not infer ongoing service state.

## Local bus journey index

`GET /api/v1/bus/network` returns normalized `{ fetchedAt, routes, coverage }`. Each direction has a route code/name, company, circular flag and ordered stops with exact station codes, names and coordinates. The explicit 2026-11-10 build read 90 DSAT catalog routes and all 111 expected directions (69 circular and 21 bidirectional routes). The snapshot contains no vehicle positions, source tokens or raw upstream fields. `fetchedAt` is the topology build time. Response metadata is the time the adapter retrieved this file; a cache refresh does not renew the topology's date.

The current official point-to-point site was found through the official bus homepage's `getMenuList.html` response: `https://bis.dsat.gov.mo/pointToPoint/pointToPoint.html`. Its scripts use `/ddbus/pointsearch` with origin and destination coordinates. The app does not relay private coordinates to that service. The older BRES page redirects and its remaining JavaScript refers to an internal environment. These observations do not establish a supported public journey-planning API contract.

`npm run build:bus-network` deliberately rebuilds the file with at most four concurrent official reads. It requires every expected direction to succeed before replacing the existing snapshot. `coverage.loadedRoutes` counts catalog routes for which every requested direction succeeded; `missingRoutes` identifies incomplete or unverified seasonal routes. The runtime uses the existing shared cache and makes no all-network upstream fan-out per page or journey search. See ADR 0012.

Journey calculation runs in the browser. Station selection uses exact platform codes by default. A location endpoint considers every indexed stop within 1 km straight-line distance. With the explicit `includeNearbyStops` option, a station endpoint also includes every indexed platform within 1 km of that selected station; access/egress distances measure from the originally selected platforms. Direct journeys and at most three transfers use forward published stop order, including repeated loop stops; the planner never joins the last listed stop to a new trip. Transfers require an identical station code, so nearby transfer platforms without a verified walking path are not joined. Access/egress distances are straight-line measurements, not walking routes or times. After the service-hour check, results rank by ridden stop edges plus one comparison point per 100 m of endpoint walking and six points per transfer (not time estimates), and return at most six bus/direction combinations. Each combination keeps its first ranked boarding, alighting and transfer choice. Each leg's `terminalName` is the last published stop name for that route/direction. Results do not claim the fastest trip, current service availability, arrival minutes or fare. The chosen live route view checks current published stop suspensions separately. An empty result means no match in this dated, limited index, not proof that no public transport route exists.

Reviewed terminal hours were transcribed from DSAT route sheets on 2026-11-11 for 2A, 3 (both directions), 61, 101, 102, N1A, N1B, N2, N3, N5 and N6. A route direction can expose `serviceWindows` as pairs of inclusive first and last departure minutes in Macau time. A smaller end minute denotes an overnight window. The planner reads the current time in `Asia/Macau` on every search submission, excludes known windows that do not cover that time and ranks fully reviewed options first. It has no user-selected departure time; each result retains the time of its search. It does not estimate departure at intermediate stops or guarantee a transfer. See ADR 0014.

The 2026-11-10 journey accuracy review re-read the official location arrays for 3A direction 0 (36 stops), MT5 direction 0 (20) and 25 direction 0 (50). Every station-code position matched the snapshot. The earlier ranking put M138 to M263's 30-stop 3A loop before a 9-stop 3A/MT5 transfer at M69/2. Ranking by ridden stop edges fixes that counterexample without inferring travel time. `docs/qa/resident-workspace/bus-journey-accuracy.json` records the bounded comparison.


### Macau place and walking snapshot

`data/walking-network.json` contains named public map features, street segments, aliases, date and a normalized directed graph. The 2026-11-09T21:22:17Z extract was processed with `python3 scripts/build-walking-network.py <macau-latest.osm.pbf>` (pyosmium). Its derived database is available in the repository and API under the [Open Database License](https://www.openstreetmap.org/copyright), © OpenStreetMap contributors. The application code is separate. Rebuild from the source extract to update coverage.

Search and route calculation run in the browser. The graph connects only shared OSM nodes and respects mapped pedestrian restrictions. Eligible endpoints snap within 55 m, favouring the main connected network. Named areas prefer mapped public entrances and otherwise use an approximate centre or boundary. Dashed endpoint links indicate approximate access. Distance includes those links. Map coverage, entrance accuracy and current access conditions vary. This graph does not provide current closure or accessibility data.

For a named-place journey, candidate platforms are within 1 km straight line and require a mapped access or egress path of at most 1 km. Explicitly selected stops keep their existing exact-match behavior unless nearby stops are enabled. Bus routes follow the official ordered topology and transfer at the same platform. Walking-only results are independent of bus availability.

## News transport and refresh, 2026-11-13

The `www.dsat.gov.mo` server sent an incomplete TLS chain to Node 22. The app now supplies its DigiCert public intermediate through a pool scoped to that exact HTTPS origin, retaining Node roots and hostname, expiry and chain checks. The certificate is server-only; no TLS verification bypass or global trust-store change is used. These direct endpoints reject redirects. See ADR 0015. The same exact-origin transport also serves the existing DSAT parking source.

`official-news` and `notices` now have a 60-second shared-cache TTL. Visible pages poll about every minute with the existing jitter, hidden-page pause and failure backoff. Manual refresh reads the same shared cache. A publisher change can therefore take roughly two polling/cache intervals to appear; this is not an immediate push feed. Stale retention remains one hour for RSS and one day for arrangements, visibly marked with the last successful retrieval time.

The DSAT RSS parser accepts the observed `<description type="html">` text node. Arrangements sort by publication date across categories, so an older keyword-labelled incident cannot hide newer bus changes. Publication dates remain distinct from retrieval and effective dates. A successful local API check returned 20 RSS items with both feeds available and 60 arrangements on November 13. This does not verify production or incident completeness.

The assistant's common Chinese/English origin/destination requests are parsed in the browser. Explicit endpoint names are resolved against the same local place/stop index as the planner. A unique exact place or platform can be selected automatically; ambiguous or unknown names require a user choice. Missing endpoints are not invented. Route calculation and coordinates stay in the browser, including when the remote AI provider is unavailable. General traffic questions still use the documented assistant provider and normalized snapshot.

Assistant publication timestamps are serialized to UTC+08:00 before the provider call, preserving the instant and the Macau calendar date. Arrangement lists publish dates only, so their UI and provider context omit the synthetic midnight time. RSS retains its supplied publication time. The public source APIs keep their ISO timestamps. The prompt requests practical next actions and omits learning exercises unless asked.

The assistant reads the LRT network only for explicit rail or named-line questions. A cold Overpass read can take 60 seconds per endpoint; news, weather and bus questions must not wait for that unrelated network. Other snapshot sources retain their existing cache and fallback policies. Tests verify both exclusion for news and inclusion for a named LRT line. See ADR 0016.

## Model journey planning (2026-11-13)

- `POST /api/v1/assistant/journeys` accepts `question`, `locale`, optional current `origin` coordinates and resolved `destinationId`; manual recovery uses `originQuery` or `originId`. Input coordinates, string lengths and provider JSON are validated. Responses are normalized `traffic`, `location`, `choose`, `clarify` or `plans` envelopes with `Cache-Control: no-store`, using the existing assistant/global rate limits.
- The first model call extracts destination search names and an explicitly named origin. The app resolves against `walking-network` and `bus-network`; ambiguous results are choices. Location is requested only for a resolved trip without an explicit origin. The second model call receives origin/destination coordinates, question, Macau current time, dated network fields, candidate legs/stops/walking distances and diversion-check freshness. It returns up to three ranked candidate IDs and explanations in JSON mode. Unknown/duplicate IDs, insufficient alternatives or malformed JSON fail visibly. No local answer is silently substituted for a model failure.
- The server reuses the same direct/up-to-three-transfer/walking functions as the manual bus planner. Reviewed terminal hours are checked against now. `bus-diversion-{routeName}` keeps its existing five-minute cache; reported suspended boarding/alighting stops exclude a candidate. Missing or stale suspension checks remain explicit. Opened journeys continue the existing live leg polling. If an endpoint has no mapped connection to any nearby bus stop, bus options use explicitly labelled straight-line access distances; no pedestrian geometry is invented. Dated topology, missing routes, unreviewed hours and OSM path closures remain limitations.
- The external provider endpoint, credentials and configuration are unchanged. JSON output uses `response_format: { type: "json_object" }` and a bounded 1,800-token output budget. The app does not persist question/location/plan results or send location to the generic traffic-question endpoint. Provider retention is outside the app's control. See ADR 0017.
- Unresolved journey names receive one additional batched interpretation call with the question and unmatched names. The same provider proposes canonical search names for typing errors, Cantonese homophones and transcription mistakes. The server validates the correction schema and input-query identity, then resolves only catalogue-backed places; it accepts no model coordinates or IDs. Related candidates for corrected names remain choices. A known destination alias skips correction of unused aliases; selected place IDs bypass interpretation. This applies to single journeys, ordered stops and day-trip endpoints, with unchanged cache and rate-limit policy. Provider/JSON failures remain visible failures.

## Ordered journeys and day trips (2026-11-14)

The same assistant endpoint additionally accepts validated `trip` and `previousTrip` drafts. New normalized responses are `trip-details`, `trip-choice`, `trip-location` and `itineraries`. Existing single-destination responses remain unchanged. Drafts contain at most eight ordered destinations, optional stay durations, and day-trip date/time/preferences. No draft, position or result is persisted or cached. Follow-up text may modify the selected itinerary in request memory. Unknown or ambiguous places require a choice, retaining the other destinations.

`cultural-places` has seven reviewed heritage places. Opening rules were read on 2026-11-14 from [official opening hours](https://www.wh.gov.mo/cn/content/visitor/) and [Mandarin's House visitor information](https://www.wh.mo/mandarinhouse/cn/visitInformation/).
